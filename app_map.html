text_to_ontology → ontology.ttl

A deliberately small pipeline that reads text files, asks an LLM to extract entities, relations, and literal facts, then merges them into a single RDF/OWL/SHACL/SKOS Turtle graph. This page maps every file, class, function, and constant in the repository.

1 What this app is, in one sentence

The repository splits into three layers that mirror its history and its plan:

Run pipeline — the code ontology.py actually executes to build the graph — plus a set of read-only tools that derive smaller views of an existing graph (partition → skeleton / patterns), which the pipeline does not call yet.

3 The run pipeline — module by module

The order below is the order the code imports and calls it. Every arrow in the diagram above is an import or a call across these files.

entry ontology.py

The command line and the run loop. Parses arguments, opens the graph, iterates files, and prints progress.

  • main()argparse → open_graph → find_text_files → loop { read → model_name → parse_source → merge_into_graph → save_graph } → summary
details args: source (Path, required), graph (Path, default ontology.ttl). Catches RuntimeError/OSError → exit 1. Skips blank files.

io ingest_sources.py

Finds and reads the source material before anything is parsed.

  • find_text_files(source, graph_path)direct file → as-is; directory → recursive, sorted, extension-filtered, graph excluded
  • read_source(path)utf-8 with errors="replace"
  • TEXT_FILES{.txt .md .rst .csv .json .jsonl .yaml .yml .xml .html .log}

prompt source_parse.py

Turns one source text into a strictly-shaped JSON prompt and returns the model's answer.

  • make_prompt(text, graph)embeds source + entity_catalog + existing property labels + the JSON contract
  • parse_source(text, graph)ask_llm(make_prompt(...))
JSON contract the LLM must return entities[] {id, name, kind, description, aliases[], existing_id} · relations[] {subject, predicate, object} · facts[] {subject, predicate, value}

llm llm.py

Tiny stdlib OpenRouter client — no SDK, just urllib.

  • load_env(path)parse .env KEY=value lines into os.environ (setdefault)
  • model_name()read OPENROUTER_MODEL or default
  • ask_llm(prompt)POST to chat/completions, temp 0, returns parsed JSON (also strips ```fences```)
  • DEFAULT_MODEL"openrouter/pareto-code:nitro"

lookup entity_lookup.py

Decides whether one parsed entity is already in the graph (the resolution fallback for the LLM's guess).

  • identity_key(text)NFKD → ascii → lowercase, strip non a-z0-9
  • entity_catalog(graph)list of {id, names, kind, description} for every onto:Entity
  • identify_entity(entity, catalog)① existing_id ② unique exact name+kind ③ unique close spelling (≥0.96)

merge graph_merge.py

Writes one parsed result into the canonical graph. Returns the four counts printed by the CLI.

  • slug(text)URI-safe identifier ("Acme Corp." → acme-corp)
  • label(text)camelCase / snake_case → readable ("worksFor" → "works For")
  • new_entity_uri(graph, name)slug + numeric suffix until unused
  • merge_into_graph(graph, data)merge entities → relations → facts; returns (new, resolved, relations, facts)

lifecycle graph_management.py

Open, seed, name, and save the one canonical Turtle graph; owns the URI namespaces.

  • bind(graph)bind the 10 prefixes
  • open_graph(path)parse existing, else seed base ontology + SHACL shape
  • save_graph(graph, path)serialize Turtle
namespaces BASE, ONTO, ENTITY, CLASS, RELATION, FACT — all under http://example.org/text-ontology/
What a merged entity looks like. Every new entity is typed onto:Entity + owl:NamedIndividual + skos:Concept + a class:<Kind>; the Kind class is auto-declared as an owl:Class subclass of onto:Entity. Relations become relation:* owl:ObjectPropertys; facts become fact:* owl:DatatypePropertys.

4 Read-only tools — deriving smaller views

These generalize an existing graph without ever writing to it. They are the “Proposal 2” layer from the repo's notes and are not called by the pipeline.

partition graph_partition.py

Splits one source graph into schema, instance, and support views. Every triple lands in exactly one view (lossless, disjoint, read-only).

  • owned_nodes(graph, root)root + reachable blank nodes
  • support_roles(graph)ontology metadata + SHACL shapes
  • restriction_roles(graph)blank-node OWL restrictions
  • schema_roles(graph, restrictions)declared/axiom-named schema resources
  • instance_roles(graph, schema)individuals typed by class/metatype
  • partition_graph(source_graph)→ (schema, instance, support)
  • choose_view(triple, …)classify one triple by decreasing certainty
sets SCHEMA_TYPES · SUPPORT_TYPES · SCHEMA_AXIOMS · ANNOTATIONS · RESTRICTION_TARGETS
output & how it's used

Output: three rdflib.Graphs returned as a tuple — schema (TBox), instance (ABox), support (ontology header + SHACL shapes) — each with the source prefixes bound. Lossless and disjoint: every source triple appears in exactly one view.

Use: the first step of the “separate TBox/ABox” workflow. Feed schema to the skeleton and patterns tools, feed instance to the patterns tool, and keep support (metadata + constraints) isolated so it never pollutes the class/property view.

skeleton graph_skeleton.py

Copies only the explicit structural core (classes, object/datatype properties, subclass/domain/range, labels, supported restrictions) into a smaller graph. No inference.

  • supported_restriction(schema_graph, node)a complete supported restriction, or None
  • structural_triples(schema_graph)retained declarations + axioms + named resources
  • create_graph_skeleton(schema_graph)→ compact graph, subset of input
sets SKELETON_TYPES · NAMED_AXIOMS · ANNOTATIONS · SUPPORTED_CONSTRAINTS (someValuesFrom, allValuesFrom, hasValue, cardinality×3)
output & how it's used

Output: one compact rdflib.Graph holding only the explicit structural core — class/property declarations, subClassOf/domain/range axioms, labels & definitions, and complete supported OWL restrictions. Always a subset of the input schema; nothing is inferred.

Use: the “semantic skeleton” / first generalization. It is the small, individuals-free schema you can hand to an LLM or agent as context, or the input to OWL module extraction — just Class →property→ Class structure without the data noise.

patterns graph_patterns.py

Summarizes how instance data actually uses its properties — observations, not axioms. Produces class→property→range records with evidence.

  • eligible(predicate)domain predicate vs. modeling metadata
  • ancestors(schema_graph, class_)explicit subClassOf closure
  • usable_classes(…)most specific domain classes (drops metatypes)
  • subject_classes(…)classes to report a subject under
  • object_ranges(…)(kind, range) pairs: class / datatype / unknown
  • class_populations(…)distinct individuals per class
  • observed_relationships(…)→ sorted list of pattern records
  • pattern_record(key, counts, population)occurrences, distinct subjects, coverage, cardinality min/median/max
sets METATYPES · STRUCTURAL · EXCLUDED (excludes onto:kind)
output & how it's used

Output: a sorted Python list[dict] — one record per observed class→property→range pattern with subject_class, predicate, range_kind (class / datatype / unknown), range, occurrences, distinct_subjects, class_population, coverage, and cardinality_min/median/max.

Use: empirical schema induction. See what the data actually does (e.g. “Person —works for→ Organization ×18, coverage 0.5”), rank by coverage/frequency, fill in missing domain/range, or turn high-coverage patterns into SHACL shapes.

How the three compose — what originates from what

They are not three independent analyses; they are a two-stage pipeline. The merged graph is the single origin. partition_graph() is the only tool that reads it, and it produces the two inputs (schema + instance) that the other two tools consume — each tool takes a different slice of that output.

the merged graph (origin) read-only tool input / output support view — not consumed

chain origin → consumer → product

  • graphontology.ttl is the single origin — produced by the write pipeline.
  • partitionreads the whole graph → emits schema, instance, support.
  • skeletonconsumes schema only → create_graph_skeleton(schema).
  • patternsconsumes schema + instance → observed_relationships(schema, instance).
  • supportconsumed by neither — kept apart so metadata/constraints don't leak in.

complement declared vs. observed

The skeleton and the patterns answer two different questions about the same schema slice:

  • skeletonwhat the ontology explicitly claims (asserted axioms, nothing inferred).
  • patternswhat the data actually does (usage, coverage, cardinality).
  • gapa pattern with no matching skeleton axiom = a missing domain/range to add.
  • feedbackhigh-coverage patterns can later become SHACL shapes and re-enter the schema.
Guarantees the tests enforce. The partition is lossless and disjoint (union = input, no overlap, input never mutated). The skeleton is always a subset of its schema input with nothing inferred. Patterns never write to disk, never drop rare patterns, and sort deterministically.
