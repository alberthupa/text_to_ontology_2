text_to_ontology — full data flow

One run of python ontology.py <source>, stage by stage. Each card shows what enters the module, what happens inside, and what leaves it. The loop body (steps 4–11) executes once per source file.

write pipeline read-only / context external LLM validation gate
1

ontology.py — main()

entry / run loop
in
  • argv: source path, graph path (default ontology.ttl)
inside
  1. parse args, open the graph (step 2)
  2. discover source files (step 3)
  3. for each file: run the loop body (steps 4–9)
  4. blank files are skipped; saves after every file
out
  • graph object + ordered file list
  • exit 1 on any validation failure
↓CLI args
2

graph_management.py

graph lifecycle
in
  • graph file path
inside
  1. open_graph(path) — parse existing Turtle, or seed base ontology + SHACL shape
  2. bind() — bind prefixes: BASE ONTO ENTITY CLASS RELATION FACT
out
  • rdflib Graph (the canonical graph)
↓Graph — everything downstream reads or writes this one object
3

ingest_sources.py

io
in
  • source path (file or directory)
  • graph path (to exclude it from discovery)
inside
  1. find_text_files() — direct file as-is, or recursive sorted scan filtered by TEXT_FILES extensions
  2. read_source(path) — utf-8 with errors="replace"
out
  • ordered list of paths → raw text per file
↓raw source text (one file at a time — loop body starts here)
4

source_concepts.py

read-only
in
  • raw source text
inside
  1. extract_source_concepts(text) — tokenize, find heading mentions, phrase runs, keywords
  2. weight & rank: mention 3.0 / phrase 2.0 / keyword 1.0, cap at 40
out
  • concepts: [{text, normalized, kind, weight, origin, position}]
↓concepts — "what this text talks about", no RDF involved
5

task_context.py — build_task_context()

read-only
in
  • source text
  • concepts (step 4)
  • current graph → ontology_views.build_ontology_views() → {schema, instance, support, skeleton, patterns}
inside
  1. build indexes over the views (names, texts, schema, resources)
  2. select_task_context() — match concepts against classes/properties/entities via 8 priority tiers (direct name/label/alias first, bounded expansion after)
  3. attach usage patterns, resources, examples, labels
out
  • ContextPackage {concepts, schema, patterns, resources, examples, labels, diagnostics}
↺ this is where the graph feedback loop lands: the graph built so far is re-read (via views) before every file, so each prompt sees everything merged by previous files.
↓ContextPackage — the selected slice of the graph, relevant to this file
6

context_render.py + prompt_budget.py

read-only
in
  • ContextPackage (step 5)
  • budget: total 30k, context 1.4k tokens, 4k output reserve
inside
  1. render_context_items() — package → compact text lines, declared structure kept apart from observed usage; delimiters defused
  2. fit_context_items() — keep only complete items (with dependencies) that fit the token ceiling, in priority order
  3. assemble_context() — fixed section order, empty sections omitted → also derives existing_ids
out
  • {text: context block, budget, existing_ids}
↓context text + existing_ids — what the LLM is allowed to see and reuse
7

source_parse.py → llm.py

external LLM boundary
in
  • raw source text
  • context text (step 6)
inside
  1. make_prompt() — instructions + context block (with CONTEXT_RULES) + strict JSON contract + the source
  2. parse_source() → ask_llm() — POST to OpenRouter, temp 0, strip code fences, parse JSON
out
  • raw LLM answer: {entities[], relations[], facts[]}
  • entities carry {id, name, kind, description, aliases, existing_id}; every record carries confidence 0.0–1.0
↓candidate JSON — untrusted model output, nothing merged yet
8

candidate_validation.py

validation gate
in
  • candidate JSON (step 7)
  • current graph (read-only check)
  • allowed existing_ids (from step 6)
inside
  1. normalize containers, text, ids; require numeric confidence in [0, 1] per record
  2. check internal references (relations/facts point to declared entities)
  3. exact dedupe within the answer
  4. reject URI-role/type collisions
  5. keep graph-exact candidates — merge policy plans their corroboration
  6. any error → whole package rejected: no plan, no merge, no save, exit 1
out
  • {valid, candidates, issues, counts}
  • on failure: format_validation_failure() → deterministic CLI error
↓validated candidates — normalized, deduped, proven conflict-free
9

merge_policy.py — build_provenance() + plan_graph_merge()

read-only planning
in
  • validated candidates (step 8)
  • current graph (the complete catalog)
  • source path, text, model name
inside
  1. build_provenance() — source path + sha256, model, policy version
  2. resolve_entities() — per entity: explicit id → unique exact match → ambiguous/kind-collision/close-spelling review → new (confidence ≥ 0.80) or review with a provisional URI; earlier accepted entities join a virtual catalog; URIs reserved so new entities cannot collide
  3. per assertion: exact-triple duplicate → functional/inverse-functional conflict review → below-threshold review → accept
  4. build sha-addressed audit triples (onto:ExtractionEvent, onto:MergeCandidate)
out
  • the MergePlan: identities, entity summaries, relation/fact outcomes, domain_triples, audit_triples, counts, diagnostics
  • nothing has been written yet
↓a complete merge plan — every decision made, nothing materialized
10

graph_merge.py — apply_merge_plan()

materialize into a copy
in
  • current graph + the MergePlan (step 9)
inside
  1. copy namespace bindings and every source triple into a fresh graph
  2. assert only the plan's decided domain and audit triples — no identity or conflict logic here
  3. report counts: new / resolved / relations / facts / metadata / duplicates / review / audit triples
out
  • updated graph copy + counts — the input graph stays triple-identical
↓updated graph copy
11

graph_management.py — save_graph()

output
in
  • updated graph copy + path
inside
  1. serialize to a temporary sibling file, then atomic os.replace — after every file; a failed save leaves the old file usable
  2. only after a successful save does the copy become the next file's active graph
out
  • ontology.ttl — the single canonical graph
Loop back. After the save, the run returns to step 3 for the next file — and steps 4–5 re-read the now larger graph through the views. Each successive prompt therefore sees everything merged by the files before it.

side chain — derived views (read-only, feeding step 5)

Rebuilt from the current graph before every file. Never writes; each stage is deterministic and tested.
