text_to_ontology → ontology.trig

A deliberately small pipeline that reads text files, splits each into reproducible windows, selects the small slice of the current graph that a window relates to, asks an LLM to extract entities, relations, and literal facts with per-record confidence, validates the reply, admits accepted assertions into a document-local staging graph, then reconciles, SHACL-validates, plans identity against the whole canonical scope, and publishes target / provenance / review graphs in one atomic call. This page maps the repository.

Python 3.12 · 35 source files depends on rdflib + pyshacl LLM: OpenRouter (Pareto router) output: ontology.trig 31 test files · 773 cases
M7 document publication (current): windowing.py + source_staging.py build one provisional graph per document. source_reconciliation.py produces the complete-document report, source_validation.py gates it with SHACL, document_merge.py decides identity once against the full canonical scope, and document_publication.py publishes target, provenance, and review graphs in one atomic store.publish(). --dry-run returns the same plan without writing. TriG is the default; Turtle output keeps legacy compatibility.
Window gates: every window's answer must pass candidate_validation.py (messy answers are sent back for bounded self-repair by repair.py). The final ontology is never written while windows run — a triple-level snapshot proves it stayed unchanged — and a non-conformant source (SourceValidationError) or proposed data (PublicationValidationError) leaves the dataset byte-identical.

1 What this app is, in one sentence

The repository has four layers built on one small public API:

Run pipeline — the packaged code cli.py → api.py → pipeline.py executes to build the dataset — plus a context-selection layer (what one source window needs to see, layered with (this document) staging knowledge), a validation gate every LLM answer passes, a merge-policy planner that decides identity, acceptance, and audit read-only, and a set of derived-view tools (partition → skeleton / patterns) the selection layer and the viewer read.

Frontend and backend

One rule: the backend owns every fact and every decision; the frontend owns pixels and input. The page never decides what matters in a graph, never validates, never writes, and never calls a model. The backend never emits markup and never knows a button exists.

frontend pixels and input only

Two files the browser runs. They parse RDF to draw it, apply declarative view directives, and call named operations. No model calls, no validation, no writes, no idea which part of the graph matters.

  • frontend/triple-lens.htmlthe viewer: RDF parser, layout, filters, details, and window.__lens (applyView / clearFiles / fileNames)
  • frontend/studio.jsthe studio frontend: top-bar actions, dialogs, the conversation column; calls api/op/<name>, applies view directives
  • frontend/studio.cssits styles
  • nevera model call, a rule re-implementation, a write, a rendering decision from the backend

backend every fact and every decision

Python only. It owns the state, the relevance, the prompts, the model calls, the validation, the patches and the provenance - and it publishes each capability as one named operation. It never emits markup.

  • workspace.pystate, jobs, chat session, pending patches
  • operations.pythe capability registry and its manifest
  • graph_scope.py · graph_chat.pyrelevance and one bounded subgraph per question
  • graph_edit.py · prompts.py · vocabulary.pypatches, editable prompts, the frozen starter vocabulary
  • studio.pytransport only: GET/POST /api/op/<name>, page and assets
  • two boundariesnamed operations in; view directives out
Adding a capability is three steps, and only the last is frontend: one def _thing(workspace, payload) in operations.py, one Operation("thing.do", …) line, one button in studio.js. studio.py never changes. If the feature should change the picture, it returns a view directive - {replace, files, mode, focus, filters, hideIsolated, clearFilters, resetFilters} - and the panel hands it to window.__lens.applyView. The detailed map is docs/current_architecture.md §1.1.

3 The run pipeline — module by module

The order below is roughly the order the code imports and calls it. Every window plus the complete-document stages appear in the diagram above.

entry cli.py + api.py + pipeline.py

The CLI is a thin adapter over the one public function; the pipeline owns the per-document loop, the protocols, and the result dataclasses.

  • cli.main(argv)parse → adapters → run_text_to_graph → exit code
  • api.run_text_to_graph(request, store, extractor, reporter)→ RunResult
  • pipeline._process_document / _extract_window / _admit_windowthe windowed document loop
details args: source (required), graph (default ontology.trig), plus -v, --report, --dry-run. Blank files are skipped. Each complete document is staged, reconciled, SHACL-validated, merged once, and published as one atomic named-graph replacement bundle.

io ingest_sources.py

Finds and reads the source material before anything is parsed.

  • find_text_files(source, graph_path)direct file → as-is; directory → recursive, sorted, extension-filtered, graph excluded
  • read_source(path)utf-8 with errors="replace"
  • TEXT_FILES{.txt .md .rst .csv .json .jsonl .yaml .yml .xml .html .log}

windows windowing.py

One source file becomes one document with a content-derived ID, then reproducible overlapping windows. Source-only: text, digests, offsets.

  • make_source_document(name, raw_text, …)id = doc-<sha256[:16]>
  • plan_windows(document, config)block → sentence → hard chunk; greedy overlap packing
  • WINDOW_STRATEGY_VERSION2 · target 800 · overlap 100 tokens

staging source_staging.py

One provisional graph per document while its windows are extracted. Nothing canonical changes during windowing.

  • plan_window_admission(source_graph, candidates, …)merge plan vs staging graph only; provisional IRIs
  • layered_context_text(canonical, source, budget, …)one budgeted block; source items marked "(this document)"
  • retain_staging(store, doc_id, graph_path)optional failure sidecar .staging/<doc>.trig

prompt source_parse.py

Turns a window plus its selected context into a strictly-shaped JSON prompt. No rdflib, no entity_lookup.

  • context_block(context_text)selected context headed + CONTEXT_RULES ('' when empty)
  • make_prompt(text, context_text="")instruction + context + JSON contract + SOURCE
  • parse_source / parse_promptask_llm(make_prompt(...))
JSON contract the LLM must return entities[] {id, name, kind, description, aliases[], existing_id, confidence} · relations[] {subject, predicate, object, confidence} · facts[] {subject, predicate, value, confidence}

llm llm.py

Tiny stdlib OpenRouter client — no SDK, just urllib. Environment loading lives here.

  • load_env(path)parse .env into os.environ (setdefault)
  • model_name()read OPENROUTER_MODEL or default
  • ask_llm(prompt)POST chat/completions, temp 0, returns parsed JSON (strips fences)
  • OpenRouterExtractormodel() / extract(prompt) adapter
  • DEFAULT_MODEL / SYSTEM_PROMPT"qwen/qwen3.5-35b-a3b:nitro" / "Extract knowledge. Return only JSON."

repair repair.py

Bounded self-repair: an unparseable or contract-violating answer is sent back with its deterministic issue list for the model to fix, under the same gate.

  • repair_prompt(original, raw_problem, issues)correct-JSON-only instruction
  • extract_validated(extractor, prompt, validate, max_repair_attempts)extract → validate → repair loop
  • ExtractionConfig.repair_attemptsdefault 2 (0 disables)

gate candidate_validation.py

A read-only gate between the LLM and any planning. Normalizes, dedupes, requires numeric confidence in [0,1], rejects provable conflicts — never calls identify_entity(), never writes.

  • validate_candidates(data, graph, allowed_existing_ids=(), vocabulary=None)→ {valid, candidates, issues, counts}
  • vocabulary (data-only)undeclared kind / relation / fact → error naming the declared names
  • format_validation_failure(result)deterministic CLI error (no raw response)
passes container → entity/relation/fact normalization (＋ confidence) → references → label/role/type collisions → exact dedupe → graph-URI compatibility. Graph-exact candidates are kept so policy can plan corroboration.

evidence candidate_graph.py

One validated package → one deterministic, inspectable RDF candidate graph with assertion and evidence kept apart.

  • build_candidate_graph(candidates, doc_id, window_id, activity_id, model, …)prov:Collection records + rdf:Statement reification + DQV confidence
  • provisional_entity_iri(doc_id, local_id)stable provisional IRI
  • literal_value(value)conservative typed literals (real ISO dates only)
  • CANDIDATE_MAPPING_VERSION2

policy merge_policy.py

Read-only planner between validation and materialization. Decides every identity and assertion outcome against the given graph, and builds deterministic audit/provenance triples — without mutating anything.

  • build_provenance(path, text, model){source_path, source_sha256, model, policy_version}
  • plan_graph_merge(graph, candidates, provenance, …, vocabulary=None)→ the MergePlan
  • vocabulary setdata-only: no class or property declaration is planned
  • resolve_entities(candidates, graph, …)identity decisions via entity_lookup.identity_decision
  • AUTO_ACCEPT_MIN_CONFIDENCE / MERGE_POLICY_VERSION0.80 / 2
decisions

identity: existing / new / review (close spelling never auto-merges) · assertions: accept / duplicate / review — below-threshold confidence goes to review; exact existing triples corroborate; functional conflicts review; existing labels/descriptions never overwritten.

audit: onto:ExtractionEvent ＋ onto:MergeCandidate per record (sha-addressed URIs, no timestamps, no raw text) — always in the support partition.

lookup entity_lookup.py

Identity decisions for one parsed entity. Close spellings only produce review evidence; kind mismatch blocks resolution.

  • identity_key(text)NFKD → ascii → lowercase
  • entity_catalog(graph){id, names, kind, description} per onto:Entity
  • identity_decision(entity, catalog, planned_catalog, …)→ {status existing|new|review, method, identity_score, suggestions, reason_codes}
  • identify_entity(entity, catalog)legacy URI-or-None wrapper

merge graph_merge.py

Materializes an already-complete plan into a copy of the graph — no identity or conflict logic of its own.

  • apply_merge_plan(source_graph, plan)copy bindings＋triples → assert domain＋audit triples → (graph copy, counts)
  • slug / label / class_uri / class_triplesshared helpers
  • merge_into_graph(graph, data)legacy compatibility path for direct callers

gate source_reconciliation.py

One plain, deterministic report for a complete document staging graph.

  • reconcile_document(doc_id, source_graph, candidate_graphs, plans)entities, aliases, duplicate assertions ＋ independent supports, unresolved, conflicts
  • build_source_artifact(document, source_graph, windowing, models)canonical N-Triples ＋ digest metadata
  • SourceGraphArtifactinspectable deterministic export

gate source_validation.py

The SHACL gate over one complete source graph before any final planning.

  • validate_source_graph(source_graph, shape_graphs)pySHACL over a copy, inference none
  • combine_shape_graphs(shape_graphs)configured shapes → one isolated input
  • SourceValidationResult / SourceValidationErrorconforms ＋ report; error carries artifact/report/sidecar

merge document_merge.py

One final identity and merge plan per document, against the complete canonical scope.

  • build_document_candidates(doc_id, packages, plans)collapse windows → one deduped package; strongest confidence wins
  • plan_document_merge(canonical_graph, document, packages, plans, conf, planner)resolves the whole source once via plan_graph_merge
  • DOCUMENT_MERGE_VERSION1

publish document_publication.py

Compiles and atomically publishes one document-level publication: proposed SHACL, PROV/DQV remapping, review material, dry-run plan.

  • compile_document_publication(document, merge, candidates, packages, plans, roles, names, shapes)→ DocumentPublicationPlan (no mutation)
  • publish_document(store, plan)the only final write: one store.publish()
  • initial_role_graphs / canonical_graph / shape_graphsrole readers
  • LegacyTurtleDatasetStore`.ttl` compatibility adapter

sources publication_sources.py

Materializes document/file source links and summaries for published statements and resources.

  • source_records(graph, document)onto:document + onto:source-file prov:Entity records
  • materialize_sources(graph, document, merge, canonical)onto:statement/<sha> links + sourceDocument/sourceFile summaries
  • supported_triples(document_merge, canonical)accepted/corroborated only — never review

store graph_store.py

The named-graph boundary. One atomic publish replaces complete named graphs; nothing else is allowed to touch them.

Legacy single-Turtle lifecycle and the shared namespaces/seed; owns the compatibility `.ttl` path and the viewer's Turtle reading.

report run_report.py

One reporter object for compact terminal output, verbose terminal output, or file-only Markdown reports.

lock vocabulary.py

Read-only. The starter vocabulary read back out of a graph: which classes, relations, and facts ingestion may use. Nothing here writes.

  • read_vocabulary(graph)→ Vocabulary(classes, relations, facts) keyed by IRI
  • class_iri(kind) / relation_iri(p) / fact_iri(p)the starter is the naming authority: the declared IRI wins, so an imported ontology keeps its own names
  • declares_class(kind) / declares_relation(p) / declares_fact(p)may ingestion use this name?
  • class_names / relation_names / fact_names / is_emptydisplay names; "no starter yet" signal
frozen With this vocabulary, validation refuses an undeclared kind or predicate and planning emits no declaration triples: the schema, the shapes, and every class/property triple stay byte-identical through ingestion.

front door starter.py

One short paste → one checked starter ontology → one atomic publication replacing all five roles. Separate from ingestion: no source document is read here.

  • starter_prompt(text) / STARTER_PROMPTclasses + relations (domain/range) + facts (XSD range)
  • validate_starter(data)→ {valid, candidates, issues, counts} — same shape the repair loop uses
  • propose_starter(text, extractor, repair_attempts=2)prompt → repair → validated proposal
  • starter_publication(proposal, names)→ one Publication: schema / shapes / empty target, provenance, review
  • create_starter(text, graph_path, …)propose + publish
  • MIN_CLASSES / MAX_CLASSES / MAX_ASSERTIONS2 / 20 / 40
  • looks_like_rdf(name, text) · parse_rdf(text, name)import an RDF/Turtle/TriG file instead of asking: a known suffix or a content sniff decides
  • import_publication(text, name, names) · import_starter(...)our own named graphs import role for role; anything else is partitioned into schema / shapes / data / support
  • main(argv)text-to-ontology-starter [INFO|-] [GRAPH] [--model] [--import FILE]
import

A document with no class or property declaration is refused with its triple count, and the write is atomic: a bad file leaves the previous dataset untouched. An imported vocabulary keeps its own IRIs, and ingestion uses them.

edit graph_edit.py

Change the graph the way a person writes Turtle: additions are ordinary statements, a line starting with - removes one. Nothing is applied by parsing — a patch is checked, previewed with a diff, and then applied by id, so what was seen is what lands.

  • parse_patch(text)additions, - removals, shared prefixes, comments
  • preview(graph, text, source, allow_new_vocabulary, shapes)→ Patch: triples, errors, warnings, stable patch_id
  • check_patch(...)new vocabulary (locked by default), undeclared use, class/property collision, SHACL as warnings
  • publication(store, names, patch)target + provenance only: schema, shapes and review are never touched
  • provenance_for(patch)one prov:Activity per edit, one rdf:Statement per triple, prov:wasGeneratedBy / wasInvalidatedBy
  • fenced_turtle(answer) · data_turtle(graph)find a proposal in an answer; show the editable graph
safety

The applied bytes are the previewed bytes (apply takes the patch id). A chat answer's Turtle block is only ever a proposal: it is previewed, and the model's invented IRIs are exactly what the vocabulary and collision checks catch.

chat graph_scope.py + graph_chat.py

Talking to a graph, not to a model: one question selects a bounded, deterministic subgraph (the same relevance layer extraction uses), the answer is written from that subgraph only, and the transcript keeps the subgraph so anyone can see what the model was shown.

  • select(text, graph, carry_over, limits)→ Scope: nodes, triples, dropped, focus_source
  • _focus · _collect · _statementsmatched resources first, a fair share each, types and labels ranked first, a slice reserved for declarations
  • Scope.trig_text() · view() · render_for_model()the three faces: for a viewer, for a frontend directive, for a model
  • ChatSession.ask(message, graph, ask, on_step)one turn; asking is injected, so no network in here
  • transcript() · recent() · reset() · _remember()each answer keeps its subgraph (newest 20 keep the view text); the focus carries over
  • render_for_model(budget, graph)PREFIXES + NAMES once, then short statements; whole triples dropped and counted
  • MAX_TRIPLES 300 · MAX_TOKENS 6000 · MAX_FOCUS 20 · MAX_NAMES 60scope caps, the token ceiling per question; HISTORY_TURNS 6 · MAX_TURNS 200 · TRANSCRIPT_VIEWS 20
page

Each answer shows N triples selected, M of them reached the model (and what was left out) with a Show the subgraph button that puts exactly those triples on the canvas, focused; With the full graph adds them beside the dataset instead, and Show the full graph again restores it.

prompts prompts.py

Every prompt the app sends is a named template: defaults in code (the tested wording), overrides in one JSON file beside the dataset. Templates use ${context}-style placeholders, so a JSON contract edited by hand needs no brace escaping.

  • DEFAULT_PROMPTSextraction_system · extraction_user · starter · chat_system · chat_user
  • PROMPT_FIELDS / REQUIRED_FIELDSwhat a template may use, and what it must keep
  • PromptLibrary.render(name, values)the finished text; a missing value is a clear ValueError
  • validate(name, text) / advice(name, text)blocking errors and non-blocking hints for a human editor
  • set(name, text) / reset(name) / describe()atomic override file, back to default, the editor's record
  • digest(name)12 hex characters, recorded in the run configuration
  • prompts.local.jsongit-ignored, beside the dataset; a corrupt file is ignored, not fatal
wired

An edited template reaches make_prompt, starter_prompt, and the extractor's system message with no other change; the pipeline re-builds the model client per run so an edited system prompt takes effect.

studio studio.py

A deliberately plain local transport: standard-library HTTP, localhost only, no state of its own. It serves the lens page and its panel, and dispatches /api/op/<name> straight into the operation registry.

page

frontend split: triple-lens.html is the visualization (plus a documented window.__lens view API); studio.js + studio.css are the panel, loaded only when the page is served. The panel holds controls and nothing else: named operations in, view directives out.

the studio row in the top bar: dataset status, then one button per action — Starter ontology… (create from a description or import a dropped RDF/Turtle/TriG file), Add sources… (refuses RDF with a pointer back), Prompts…, Edit the graph… (Turtle, preview diff, Apply, allow-new-vocabulary) — then Clear view (unload the view, delete nothing), Reset everything, and Log. Each action is a dialog. The right-hand column is only the conversation with the graph: bubbles, a thinking indicator fed by job progress, Enter to send, each answer showing the subgraph it used and any Turtle proposal it made. Opened from disk the page is the plain viewer: no studio, no server, everything read in the browser.

the subgraph is visible: after each chat answer the canvas switches to exactly the triples the model was shown (its own file, filters cleared, focus set), and each answer keeps a Show the subgraph / With the full graph button plus a "Show the full graph again" restore. Adding a small scope beside a large dataset was invisible, which is why the default isolates it.

progress: one bar under the studio row in the top bar, labelled with the running job (the chat shows the same detail inside its thinking bubble instead). Starter: model call 1, 2… (repairs included) then the write step. Ingestion: per file and per window — n2.txt: window 1/1, asking the model → admitted → published. The panel polls progress every 400 ms and the bar only moves forward.

What a merged entity looks like. Every accepted entity is typed onto:Entity + owl:NamedIndividual + skos:Concept + a class:<Kind>; the Kind class is auto-declared as an owl:Class subclass of onto:Entity. Relations become relation:* owl:ObjectPropertys; facts become fact:* owl:DatatypePropertys. The provenance graph keeps PROV/DQV candidate evidence and onto:statement/<sha> source links; onto:ExtractionEvent + onto:MergeCandidate audit records land in the support partition; withheld candidates land in the review graph.

4 Context selection — choosing what the LLM sees

Four read-only modules plus the derived views, chained per source window — twice per window, actually: once against the final ontology, once against this document's staging graph, merged into one budgeted block with source-local items marked (this document). Nothing here writes to the graph.

concepts source_concepts.py

What one text mentions, before any ontology is opened. Free of RDF and llm, so NLP/NER/embeddings can replace it later.

  • extract_source_concepts(text)→ list[{"text","normalized","kind","weight","origin","position"}]
  • text_phrases(text, longest)word-run phrase index for boundary-safe matching
  • MAX_CONCEPTS40 · weights: mention 3.0 / phrase 2.0 / keyword 1.0

façade ontology_views.py

The five derived views as one record. Tiny façade, no logic of its own.

  • build_ontology_views(source_graph)→ {"schema","instance","support","skeleton","patterns"}
composition

partition_graph() → schema · instance · support; create_graph_skeleton(schema); observed_relationships(schema, instance).

select task_context.py

Aligns the source text with the graph and selects the relevant classes, properties, observed usage, resources, and examples as a bounded ContextPackage.

  • select_task_context(text, concepts, views, native_entities=None, limits=None)the independently testable selector
  • build_task_context(text, source_graph, limits=None)views + concepts + catalog → selector
  • DIRECT_NAME…INDIRECT8 priority tiers; relevance outranks frequency
what it returns

ContextPackage {concepts, schema, patterns, resources, examples, labels, diagnostics} — items carry id/kind/value/priority/reason/direct; a survival map (labels) means rendering never re-reads the graph.

render context_render.py

Turns the selection into compact lines the LLM can read, keeping declared structure visibly apart from observed usage.

  • render_context_items(package, namespace_manager=None)→ items with section/priority/text/dependencies
  • assemble_context(rendered_items)fixed section order, empty sections omitted
  • allowance(budget_config) / assembly_overhead(items, count_tokens)the smaller cap wins; overhead charged first
  • prepare_prompt_context(package, budget_config)→ {text, budget, existing_ids}
  • MAX_FIELD_CHARACTERS240 · delimiters defused so graph text can't forge a heading/fence

budget prompt_budget.py

Token estimate, allowance, and packing — only complete items that fit, in priority order. The counter is swappable for a real tokenizer.

  • estimate_tokens(text, chars_per_token=3)ceil(len / divisor)
  • context_allowance(total, fixed, source, reserve, margin)clamped ≥ 0
  • fit_context_items(items, budget)complete item + its dependencies only; never slices
  • PROMPT_BUDGETtotal 30_000 · context_tokens 1_400 · output_reserve 4_000
How the pieces compose. source_concepts finds what the text mentions (no RDF) · ontology_views derives schema/instance/support/skeleton/patterns · task_context selects an item package via 8 relevance tiers (tiers 1–4 direct, 5–8 bounded expansion) · context_render renders it as declared/observed/ resources/examples · prompt_budget keeps only what fits the 1400-token ceiling. source_staging.layered_context_text() runs this twice per window — canonical context plus earlier-window source context marked (this document) — under one shared budget, and only canonical native resources become reusable existing_ids.

5 Derived views — the read-only foundation

Three tools generalize an existing graph without ever writing to it. They feed the context-selection layer and the standalone viewer; each is tested, read-only, and deterministic.

partition graph_partition.py

Splits one source graph into schema, instance, and support views. Lossless and disjoint: every triple lands in exactly one view. Support also captures merge audit records and source metadata.

  • partition_graph(source_graph)→ (schema, instance, support)
  • choose_view(triple, …)classify one triple by decreasing certainty
  • support_roles / restriction_roles / schema_roles / instance_rolesrole sets
output & use

Three rdflib.Graphs: TBox (schema), ABox (instance), header + SHACL + audit + source metadata (support). schema feeds skeleton + patterns; instance feeds patterns; support stays apart so metadata/constraints never leak into the class/property view.

skeleton graph_skeleton.py

Copies only the explicit structural core (classes, object/datatype properties, subclass/domain/range, labels, supported restrictions). No inference.

  • supported_restriction(schema_graph, node)a complete supported restriction, or None
  • structural_triples(schema_graph)retained declarations + axioms + named resources
  • create_graph_skeleton(schema_graph)→ compact graph, subset of input
output & use

One compact rdflib.Graph — always a subset of the schema input, nothing inferred. The “semantic skeleton”: individuals-free structure you can hand an LLM as context.

patterns graph_patterns.py

Summarizes how instance data actually uses its properties — observations, not axioms. Class→property→range records with evidence.

  • observed_relationships(schema_graph, instance_graph)→ sorted list of pattern records
  • pattern_record(key, counts, population)occurrences, distinct subjects, coverage, cardinality
  • usable_classes / object_ranges / ancestorsmost-specific classes + ranges
output & use

A list[dict] — one record per observed class→property→range pattern. Empirical schema induction: fill missing domain/range, or turn high-coverage patterns into SHACL shapes.

chain origin → consumer → product

  • graphontology.trig (any named graph, or a legacy .ttl) is the read-only origin — produced by the write pipeline.
  • partitionreads the whole graph → schema, instance, support.
  • skeletonconsumes schema only → create_graph_skeleton(schema).
  • patternsconsumes schema + instance → observed_relationships(schema, instance).
  • viewerview_ontology.py -html writes a self-contained page from view_report.build_report() data.

complement declared vs. observed

  • skeletonwhat the ontology explicitly claims (asserted axioms, nothing inferred).
  • patternswhat the data actually does (usage, coverage, cardinality).
  • gapa pattern with no matching skeleton axiom = a missing domain/range to add.
Guarantees the tests enforce. The partition is lossless and disjoint (union = input, no overlap, input never mutated). The skeleton is always a subset of its schema input with nothing inferred. Patterns never write to disk, never drop rare patterns, and sort deterministically.
