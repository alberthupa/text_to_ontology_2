text_to_ontology → ontology.ttl

A deliberately small pipeline that reads text files, selects the small slice of the current graph that each file actually relates to, asks an LLM to extract entities, relations, and literal facts with per-record confidence, validates the reply, plans every identity and merge decision read-only, then materializes that plan into a single RDF/OWL/SHACL/SKOS Turtle graph. This page maps every file, class, function, and constant in the repository.

Python 3 · 17 source files depends on rdflib only LLM: OpenRouter (Pareto router) output: ontology.ttl 16 test files · 611 cases

1 What this app is, in one sentence

The repository has four layers that mirror its history and plan:

Run pipeline — the code ontology.py actually executes to build the graph — plus a validation gate it passes every LLM answer through, a merge-policy planner that decides identity, acceptance, and audit before anything is written, a context-selection layer that chooses which part of the growing graph each source needs to see, and a set of derived-view tools (partition → skeleton / patterns) the selection layer reads.

write path the run pipeline

Executed when you run the program. Opens the graph, loops over source files, selects context, asks the LLM, validates the answer, plans the merge read-only, materializes the plan into a copy, saves.

3 The run pipeline — module by module

The order below is the order the code imports and calls it. Every arrow in the diagram above is an import or a call across these files.

entry ontology.py

The command line and the run loop.

  • main()open_graph → find_text_files → loop { read → build_task_context → prepare_prompt_context → parse_source → validate_candidates → build_provenance → plan_graph_merge → apply_merge_plan → save_graph }
  • budget_for(text)PROMPT_BUDGET ＋ source token cost
  • report_context / report_validation / report_planone-line Context: / Validated: / Planned: reports
details args: source (required), graph (default ontology.ttl). Any validation error → RuntimeError (caught → exit 1). Blank files skipped. The plan materializes into a graph copy; the copy is saved atomically and only then becomes the next file's active graph.

io ingest_sources.py

Finds and reads the source material before anything is parsed.

  • find_text_files(source, graph_path)direct file → as-is; directory → recursive, sorted, extension-filtered, graph excluded
  • read_source(path)utf-8 with errors="replace"
  • TEXT_FILES{.txt .md .rst .csv .json .jsonl .yaml .yml .xml .html .log}

prompt source_parse.py

Turns a source plus its selected context into a strictly-shaped JSON prompt and returns the model's answer. No rdflib, no entity_lookup.

  • context_block(context_text)selected context headed + CONTEXT_RULES ('' when empty)
  • make_prompt(text, context_text="")instruction + context + JSON contract + SOURCE
  • parse_source(text, context_text="")ask_llm(make_prompt(...))
JSON contract the LLM must return entities[] {id, name, kind, description, aliases[], existing_id, confidence} · relations[] {subject, predicate, object, confidence} · facts[] {subject, predicate, value, confidence}

llm llm.py

Tiny stdlib OpenRouter client — no SDK, just urllib.

  • load_env(path)parse .env into os.environ (setdefault)
  • model_name()read OPENROUTER_MODEL or default
  • ask_llm(prompt)POST chat/completions, temp 0, returns parsed JSON (strips fences)
  • DEFAULT_MODEL"openrouter/pareto-code:nitro"

gate candidate_validation.py

A read-only gate between the LLM and merge policy. Normalizes the answer, removes duplicates, requires a numeric confidence per record, and rejects provable conflicts — never calls identify_entity(), never writes.

  • validate_candidates(data, graph, allowed_existing_ids=())→ {valid, candidates, issues, counts}
  • format_validation_failure(result)deterministic CLI error (no raw response)
passes container → entity/record normalization (＋ confidence check) → reference check → exact dedupe → URI-role/type collisions → graph-exact dedupe (only with explicit ids) → finalize. Graph-exact candidates are kept so policy can plan corroboration.

policy merge_policy.py

Read-only planner between validation and materialization. Decides every identity and assertion outcome against the complete graph, and builds deterministic provenance/audit triples — without mutating anything.

  • build_provenance(path, text, model){source_path, source_sha256, model, policy_version}
  • plan_graph_merge(graph, candidates, provenance)→ the MergePlan
  • resolve_entities(candidates, graph)identity decisions via entity_lookup.identity_decision
  • AUTO_ACCEPT_MIN_CONFIDENCE0.80 · MERGE_POLICY_VERSION 1
decisions

identity: existing / new / review (close spelling never auto-merges) · assertions: accept / duplicate / review — below-threshold confidence goes to review; exact existing triples corroborate; functional conflicts review; existing labels/descriptions never overwritten.

audit: onto:ExtractionEvent ＋ onto:MergeCandidate per record (sha-addressed URIs, no timestamps, no raw text) — always in the support partition.

lookup entity_lookup.py

Identity decisions for one parsed entity. The rich identity_decision() is what the planner uses; close spellings only produce review evidence.

  • identity_key(text)NFKD → ascii → lowercase, strip non a-z0-9
  • entity_catalog(graph){id, names, kind, description} per onto:Entity
  • identity_decision(entity, catalog, planned_catalog, …)→ {status existing|new|review, method, score, suggestions, reason_codes}
  • identify_entity(entity, catalog)legacy URI-or-None wrapper

merge graph_merge.py

Materializes an already-complete plan into a copy of the graph — no identity or conflict logic of its own. Returns the counts printed by the CLI.

  • apply_merge_plan(source_graph, plan)copy bindings＋triples → assert domain＋audit triples → (graph copy, counts)
  • slug(text) / label(text) / new_entity_uri(graph, name)shared helpers
  • merge_into_graph(graph, data)legacy compatibility path for direct callers

lifecycle graph_management.py

Open, seed, name, and save the one canonical Turtle graph; owns the URI namespaces.

  • bind(graph)bind the prefixes
  • open_graph(path)parse existing, else seed base ontology + SHACL shape
  • save_graph(graph, path)serialize to a temp sibling, then atomic os.replace
namespaces BASE, ONTO, ENTITY, CLASS, RELATION, FACT — under http://example.org/text-ontology/
What a merged entity looks like. Every new entity is typed onto:Entity + owl:NamedIndividual + skos:Concept + a class:<Kind>; the Kind class is auto-declared as an owl:Class subclass of onto:Entity. Relations become relation:* owl:ObjectPropertys; facts become fact:* owl:DatatypePropertys. Each accepted source also leaves an audit trail (onto:ExtractionEvent, onto:MergeCandidate) in the support partition.

4 Context selection — choosing what the LLM sees

Four read-only modules plus the derived views, chained per source. Nothing here writes to the graph; selection narrows the prompt, never the merge.

concepts source_concepts.py

What one text mentions, before any ontology is opened. Deliberately free of RDF and no llm, so NLP/NER/embeddings can replace it later.

  • extract_source_concepts(text)→ list[{"text","normalized","kind","weight","origin","position"}]
  • text_phrases(text, longest)word-run phrase index for boundary-safe matching
  • MAX_CONCEPTS40 · weights: mention 3.0 / phrase 2.0 / keyword 1.0

façade ontology_views.py

The five derived views as one record. Nine lines of body, no logic of its own.

  • build_ontology_views(source_graph)→ {"schema","instance","support","skeleton","patterns"}
composition

partition_graph() → schema · instance · support; create_graph_skeleton(schema); observed_relationships(schema, instance).

select task_context.py

Aligns the source text with the graph and selects the relevant classes, properties, observed usage, resources, and examples as a bounded ContextPackage.

  • select_task_context(text, concepts, views, native_entities=None, limits=None)the independently testable selector
  • build_task_context(text, source_graph, limits=None)views + concepts + catalog → selector
  • DIRECT_NAME…INDIRECT8 priority tiers; relevance outranks frequency
what it returns

ContextPackage {concepts, schema, patterns, resources, examples, labels, diagnostics} — items carry id/kind/value/priority/reason/direct; a survival map (labels) means rendering never re-reads the graph.

render context_render.py

Turns the selection into compact lines the LLM can read, keeping declared structure visibly apart from observed usage.

  • render_context_items(package, namespace_manager=None)→ items with section/priority/text/dependencies
  • assemble_context(rendered_items)fixed section order, empty sections omitted
  • prepare_prompt_context(package, budget_config)→ {text, budget, existing_ids}
  • MAX_FIELD_CHARACTERS240 · delimiters defused so graph text can't forge a heading/fence

budget prompt_budget.py

Token estimate, allowance, and packing — only complete items that fit, in priority order. The counter is swappable for a real tokenizer.

  • estimate_tokens(text, chars_per_token=3)ceil(len / divisor)
  • context_allowance(total, fixed, source, reserve, margin)clamped ≥ 0
  • fit_context_items(items, budget)complete item + its dependencies only; never slices
  • PROMPT_BUDGETtotal 30_000 · context_tokens 1_400 · output_reserve 4_000
How the pieces compose. source_concepts finds what the text mentions (no RDF) · ontology_views derives schema/instance/support/skeleton/patterns · task_context selects an item package via 8 relevance tiers (tiers 1–4 direct, 5–8 bounded expansion) · context_render renders it as declared/observed/ resources/examples · prompt_budget keeps only what fits the 1400-token ceiling.

5 Derived views — the read-only foundation

Three tools generalize an existing graph without ever writing to it. They feed the context-selection layer; each is tested, read-only, and deterministic.

partition graph_partition.py

Splits one source graph into schema, instance, and support views. Lossless and disjoint: every triple lands in exactly one view.

  • partition_graph(source_graph)→ (schema, instance, support)
  • choose_view(triple, …)classify one triple by decreasing certainty
  • support_roles / restriction_roles / schema_roles / instance_rolesrole sets
output & use

Three rdflib.Graphs: TBox (schema), ABox (instance), header + SHACL (support). schema feeds skeleton + patterns; instance feeds patterns; support stays apart so metadata/constraints never leak into the class/property view.

skeleton graph_skeleton.py

Copies only the explicit structural core (classes, object/datatype properties, subclass/domain/range, labels, supported restrictions). No inference.

  • supported_restriction(schema_graph, node)a complete supported restriction, or None
  • structural_triples(schema_graph)retained declarations + axioms + named resources
  • create_graph_skeleton(schema_graph)→ compact graph, subset of input
output & use

One compact rdflib.Graph — always a subset of the schema input, nothing inferred. The “semantic skeleton”: individuals-free structure you can hand an LLM as context.

patterns graph_patterns.py

Summarizes how instance data actually uses its properties — observations, not axioms. Class→property→range records with evidence.

  • observed_relationships(schema_graph, instance_graph)→ sorted list of pattern records
  • pattern_record(key, counts, population)occurrences, distinct subjects, coverage, cardinality
  • usable_classes / object_ranges / ancestorsmost-specific classes + ranges
output & use

A list[dict] — one record per observed class→property→range pattern. Empirical schema induction: fill missing domain/range, or turn high-coverage patterns into SHACL shapes.

chain origin → consumer → product

  • graphontology.ttl is the single origin — produced by the write pipeline.
  • partitionreads the whole graph → schema, instance, support.
  • skeletonconsumes schema only → create_graph_skeleton(schema).
  • patternsconsumes schema + instance → observed_relationships(schema, instance).

complement declared vs. observed

  • skeletonwhat the ontology explicitly claims (asserted axioms, nothing inferred).
  • patternswhat the data actually does (usage, coverage, cardinality).
  • gapa pattern with no matching skeleton axiom = a missing domain/range to add.
Guarantees the tests enforce. The partition is lossless and disjoint (union = input, no overlap, input never mutated). The skeleton is always a subset of its schema input with nothing inferred. Patterns never write to disk, never drop rare patterns, and sort deterministically.
