Three Roads to Jena

Three independent proposals for turning a working pile of nineteen Python files into a modular, graph-currency pipeline. They agree on far more than they disagree — and the disagreements are the only part worth your time.

5,895 lines of Python 18 test files 318 KB ontology.ttl 1 dependency (rdflib)

Read the three as two

ox and deepseek are not independent. They share whole sentences (“already ~80% true”, “the loose files feeling”), an identical named-graph table, and migration steps 1–5 in the same order with the same size labels. deepseek is ox expanded — a directory layout, a vocabulary audit, and one extra migration step. So the apparent 3-of-3 consensus below is really 2-of-2: the ox/deepseek line and the openai line arrived at the same core independently. That is a strong signal for the core, and it means where openai stands alone, it is a genuine second opinion rather than a minority vote.

02 — Settled

What all three already agree on

Treat this list as decided. Nothing below is contested by any proposal, and most of it is a formalization of what your code does already rather than a change of direction.

  • 01
    The graph is the only currency between modules.

    Plain functions with the shape module(graph, params) → graph | data. No plugin registry, no abstract base classes, no framework. The “API” is the set of signatures.

  • 02
    One thin orchestrator owns the order; modules never import each other.

    This is the real fix for the “loose files” feeling. ontology.py:29 already is that orchestrator — it just also owns the CLI, the reporting wiring, and the budget helper.

  • 03
    A store adapter is the single new abstraction.

    rdflib in memory first, Jena Fuseki over SPARQL later, behind one boring interface. Turtle is demoted from storage to interchange. graph_management.py is 64 lines, so this swap is cheap — that file is almost the adapter already.

  • 04
    Named graphs replace read-time partitioning.

    Schema, shapes, instance, support, and optional per-source graphs. Placement becomes a write-time decision instead of re-classifying a growing dataset on every run, which is what graph_partition.py does today.

  • 05
    A window is a source text.

    Split on paragraph boundaries with ~10% overlap, process in order so window N+1 sees the entities window N created. Nothing downstream changes — which is why all three reach for it: it is the cheapest possible answer to “inputs will be very long”.

  • 06
    Provenance keys on (source sha256, window index).

    The same key buys idempotent re-runs, selective un-merge, and the ability to cite where a triple came from. Backlog items 2, 3 and 6 collapse into one design decision.

  • 07
    A seed graph is just an input graph.

    Repeatable --seed / --shapes flags; the default seed ships as a .ttl file rather than the eight hard-coded triples now in graph_management.py:31. That single change makes the future seed-builder tool decoupled by construction — anything that emits valid Turtle is a seed builder.

  • 08
    How much skeleton reaches the prompt is a parameter, not a rule.

    All three park it in the context module. ox and deepseek propose a skeleton_mode = none | relevant | full enum; openai proposes replaceable select_skeleton() strategies. Same idea, different granularity.

  • 09
    Planning stays read-only; exactly one writer applies a finished plan.

    Your merge_policy → graph_merge split survives all three proposals untouched. It is the strongest thing in the current codebase.

  • 10
    SHACL becomes an actual check.

    Today a shape is seeded and never validated against. All three add a conformance step — though not, as it turns out, in the same place.

  • 11
    Vanilla vocabularies only.

    RDF, RDFS, OWL, SKOS, SHACL, plus prov, dcterms, foaf. Project IRIs are reserved for discovered domain terms — the things being described, never the machinery describing them.

  • 12
    Migrate in small steps that each keep the CLI working and the tests green.

    And all three explicitly rule out the same things: microservices, DAG engines, plugin registries, inference engines, and parallel merge writers.

03 — Contested

Ten decisions the proposals do not share

This is the part that needs your judgement. The last column is my recommendation, weighted toward what you actually asked for and what AGENTS.md demands.

QuestionPositionsCall
Are named graph IRIs fixed or configured?

ox / deepseekFive fixed names: urn:app:schema, :shapes, :instance, :support, :source/<sha>.

openaiConfiguration supplies lists: schema_graphs, shape_graphs, data_graphs, plus one explicit target_graph.

 openai. You said future input will be “many graphs / SHACL shapes”. A single fixed urn:app:shapes contradicts that on day one. Keep the five names as defaults, not as the model.
Is there a candidate graph before merge?

ox / deepseekNo. JSON → validate → plan → triples, as today.

openaiYes. JSON is converted to a staging RDF graph immediately, and validation, SHACL, and planning all run against RDF.

 openai — and this is the single biggest difference. Your own note in ox_recommendations.md asks for “extracted subgraph before graph merge”. It is also the only way SHACL can run before anything is written.
Where does SHACL run?

ox / deepseekAfter the merge — their orchestrator pseudocode literally reads merge.apply(...) then check.report_if_requested(...).

openaiBefore publication, as a precondition of the transaction.

 openai. A check that runs after the write is a report, not a gate. Backlog item 8 asks for enforcement.
Do confidence and merge decisions belong in RDF?

deepseekYes, in the support graph, re-expressed with prov: / dcterms: instead of today's onto:ExtractionEvent and onto:MergeCandidate.

openaiNo. There is no standard property for extraction confidence, so keep it in the run report and let candidate/review graph placement carry the decision.

 Split them. deepseek is right that the audit trail belongs in the graph — it is what makes review possible, and you already write it. openai is right that no standard property exists — which argues for one narrowly-scoped app property, not for discarding the data.
How deep should the package tree be?

oxUnspecified.

deepseekFlat: pipeline.py, store.py, vocab.py, seeds/, and one modules/ folder of verb-named files.

openaiEight subpackages — source/ context/ extraction/ merge/ store/ adapters/ reporting/ tools/.

 deepseek. AGENTS.md asks for code self-explanatory to a non-advanced developer. ls modules/ printing the pipeline in order beats navigating context/select.py vs context/skeleton.py vs context/patterns.py. Split a module into a folder only when its file actually grows too big — task_context.py at 622 lines already qualifies.
Does entity identity get its own module?

deepseekNo — entity_lookup folds into plan.

openaiYes — its own read-only module with a five-tier resolution ladder and room for a later text index.

oxDoesn't say.

 openai. Your backlog note asks for a deep dive on entity resolution and deduplication. That needs its own file, its own tests, and somewhere to hang an index tier — not a section inside the planner.
Is there a callable API, or only a CLI?

ox / deepseekAn orchestrator run() that also parses arguments.

openairun_text_to_graph(request, store, extractor, reporter), with the CLI as a thin translator into one request object.

 openai. This is literally the “api-like structure” you asked for. It also makes the store, the LLM, and the reporter injectable — which tests/test_pipeline.py already wants, since main() takes a reporter today purely for that reason.
How is configuration modelled?

ox / deepseekAn implicit options object passed around.

openaiNamed dataclass records per module; only the composition root reads environment variables.

 openai, lightly. Named records beat an untyped dict, and “no module reads os.environ” is worth enforcing — llm.py breaks it today. But don't write five config classes before there are five modules.
What belongs on the store interface?

deepseekAdds store.source_already_processed(sha256).

ox / openaiSPARQL query/update, graph get/put, ttl load/export, transaction. Nothing else.

 ox / openai. “Have I seen this source?” is a one-line SPARQL ASK owned by the pipeline. Put it on the store and every backend re-implements application logic.
How rigorous is windowing?

ox / deepseekParagraph boundaries, ~10% overlap, window index in provenance.

openaiPlus character offsets, a strategy_version in the window id, a real tokenizer, a sentence-then-hard-character fallback ladder, and an explicit “never discard the tail”.

 openai. Without offsets you cannot cite a window; without a strategy version, provenance by index alone silently breaks the first time you tune the splitter. Both are cheap to add now and expensive to retrofit.

04 — Reality check

How each holds up against the code that exists

graph_management.py is 64 lines: open, bind, atomic save The store adapter is genuinely a small change. Every proposal's step 1 is correct and low-risk, and the atomic-replace behavior transfers to the memory backend unchanged.

05 — Blind spots

What none of the three covers

Six things missing from all three documents. The first one is the most important, because it is the thing you wrote down first.

The generalization agenda is missing

Your root next_steps.md lays out a real plan: separate TBox from ABox, extract locality-based OWL modules around a signature, induce an empirical schema from characteristic sets, publish derived SHACL shapes, and build purpose-specific views with SPARQL CONSTRUCT — weighted by an importance score. That is your answer to “how does the skeleton get into the prompt once texts are long”. All three proposals compress it into a skeleton_mode enum or a config block. It needs its own module producing named, rebuildable derived graphs — ontology map, relationship map with counts, domain modules, agent view. graph_patterns.py is already the seed of it.

The viewer does not survive the move

Three files and 1,665 lines of reporting assume an in-memory graph and a single self-contained page. Against Fuseki, both assumptions fail. Nobody proposes what the viewer becomes: SPARQL-backed pages, a size ceiling, or a per-named-graph view.

No packaging story

All three propose a package directory. None mentions a pyproject.toml, a console entry point, or how nineteen flat modules and eighteen flat test imports get there without a day of churn. There is no packaging in the repo today at all.

Windowing has a price nobody quotes

N windows means N LLM calls and N context builds per document. No proposal suggests a per-document ceiling, a cost line in the report, or a resume point after a failed window — even though every one of them promises that a failed window leaves committed work intact.

Failure semantics stay a sentence

“Per-window commits keep earlier work intact” appears in all three. None says what the process exits with, what the report shows, or whether a partially-processed document is resumable — which matters much more once one file becomes forty windows.

Migrating the graph you already have

318 KB of Turtle, including support triples, has to land in the right named graphs exactly once. Only openai names the step, and none identifies the tool — which, as above, you already wrote.

06 — Recommendation

Take deepseek's skeleton and openai's contracts

Neither line is complete on its own. ox/deepseek get the shape and the restraint right; openai gets the boundaries right. They are compatible — the split falls neatly along where files live versus what functions promise.

from deepseek

The flat layout — pipeline.py, store.py, vocab.py, seeds/default.ttl, and one modules/ folder whose file names read as the flow. Plus vocab.py as the enforcement point for “nothing custom”, and its vocabulary cleanup as a real migration step.

from openai

The callable run_text_to_graph() boundary with an injectable store, extractor, and reporter; per-module config records; the candidate RDF graph; graph roles as configured lists; SHACL before publication; identity as its own module; and windows with offsets and a strategy version.

from ox

The cadence. Six or seven small steps, each keeping the CLI usable and the tests green, no big-bang rewrite — and the discipline of a proposal short enough to actually be followed.

A sequence, reordered from theirs

  1. 01
    Store adapter, memory backend only.

    Route every open and save through store.py. No behavior change, all tests green. Every proposal agrees this is first, and it is.

  2. 02
    Split the CLI from run_text_to_graph(), add config records.

    Do this second, not late. It is the change that makes everything after it testable without a CLI, and it gets cheaper the sooner it happens — openai puts it in phase 1 for good reason.

  3. 03
    Move files into modules/, add vocab.py.

    One import line per test file. Do it while the module count is nineteen rather than thirty.

  4. 04
    Windowing, with offsets and a strategy version.

    The loop body runs per window; provenance gains the window key. Add the per-document cost ceiling and the resume point here, while the loop is already being touched.

  5. 05
    Candidate graph, then SHACL as a gate.

    Convert validated JSON into a staging RDF graph, validate it against the shapes, and only then plan and publish. This is where your “extracted subgraph before merge” note lands, and it must come before Fuseki, not after.

  6. 06
    Named graphs and configured graph lists.

    Write-time placement; --seed / --shapes repeatable; the default seed as a shipped .ttl. Use graph_partition.py once to migrate the existing graph, then keep it only for the viewer.

  7. 07
    Fuseki backend, opt-in.

    --store fuseki:... for real runs; memory stays the default for tests. Decide here what the viewer becomes.

  8. 08
    The derived-views module.

    The gap none of the three covers: skeleton extraction, characteristic-set induction, derived SHACL shapes, and CONSTRUCT-built task views as named, rebuildable graphs. Once this exists, skeleton_mode stops being an enum and becomes a choice of which derived view to feed the prompt — which is what you were actually describing.

If you only take one thing

Adopt the candidate graph. It is the one structural idea only one proposal has, it is the thing you independently asked for in your own backlog note, and it is what turns validation, SHACL, and review from a report into a gate. Everything else on this page is a matter of taste or timing.
